# API v1 Contract — `apps/api` ↔ `apps/web`

Source of truth for the JSON API the Next.js frontend (`apps/web`) consumes from the Laravel backend (`apps/api`). Entities match PRD §7. This is a living document — update it alongside API changes, don't let it drift.

Base URL (local dev): `http://localhost:8000/api/v1`. Configured via `NEXT_PUBLIC_API_BASE_URL` in `apps/web`.

## Auth model

- **Public read endpoints** (services, astrologers, courses, CMS content, settings, availability, chart calculation): no auth required.
- **Client account**: Laravel Sanctum token auth. `POST /auth/register`, `POST /auth/login` return a bearer token; send as `Authorization: Bearer <token>` on subsequent requests. Guest booking/enrollment (no account) is also supported — see below.
- **Admin panel** (TailAdmin, server-rendered Blade): separate session-based auth, not part of this JSON contract.
- CORS: allowed origins are the Vercel preview + production domains, configured in `apps/api/config/cors.php`.

## Conventions

- **Locale**: `?locale=en|hi|gu` query param on any endpoint returning translatable content (services, astrologers, courses, CMS). Defaults to `en` if omitted or unsupported.
- **Currency**: prices are always returned as both `price_inr` and `price_usd` (both explicitly stored per PRD §11 — never computed client-side). The frontend's currency switcher just chooses which field to display.
- **Pagination**: list endpoints return `{ "data": [...], "meta": { "current_page", "last_page", "per_page", "total" } }` (Laravel's default paginator shape).
- **Errors**: `{ "message": string, "errors"?: { [field]: string[] } }` with standard HTTP status codes (422 validation, 404 not found, 401/403 auth, 500 server).
- **IDs**: numeric auto-increment `id` plus a URL-safe `slug` for anything linked to from a page (astrologers, services, courses, posts, pages).

## Endpoints

### Settings
- `GET /settings` → site branding, supported languages, UPI ID + QR image URL, SEO defaults, currency display config. Powers the frontend's global layout (#22).

### Astrologers & Services
- `GET /astrologers?locale=` → list. `GET /astrologers/{slug}?locale=` → detail with `services[]`.
- `GET /services?astrologer_id=&locale=` → list, each with `price_inr`, `price_usd`, `duration_minutes`.
- `GET /availability?astrologer_id=&service_id=&from=&to=` → open slots (works whether that astrologer is in manual-slots or Google-Calendar-sync mode — the API abstracts the source).

### Bookings
- `POST /bookings` → body: `{ astrologer_id, service_id, slot, client: { name, email, phone }, birth_details?, birth_chart_id?, guest: boolean }`. Returns booking with `status: "pending_payment"`, a `reference_number`, and the UPI ID/QR (from Settings) for the confirmation screen.
- `GET /bookings/{id}?token=` → lookup for guests (token issued at creation) or via authenticated `/me/bookings` for account holders.
- Status values: `pending_payment | confirmed | completed | cancelled | no_show` (admin-panel-driven transitions; the public API is read + create only, no client-side status changes).

### Courses & Enrollments
- `GET /courses?type=recorded|live&locale=` → list. `GET /courses/{slug}?locale=` → detail with curriculum/modules.
- `POST /enrollments` → same pending→confirmed pattern as bookings, body: `{ course_id, client: {...}, guest: boolean }`. Response includes the same `upi_id`/`upi_qr_url` (read live from Settings) as `BookingResource`, for the confirmation screen.
- `GET /me/enrollments` (authenticated) → includes lesson access / progress for recorded courses, live session schedule/links for live courses.

Returns 201 on the first (computing) request per Laravel's resource-response convention, 200 on a cached repeat.
- `GET /charts/{id}/report?year_wise_style=&year=` (authenticated, owner-only — 403 otherwise) → downloads a PDF (`application/pdf`) Kundali report assembled from the chart's already-computed `result` plus a few sections computed fresh at request time (doshas, Sade Sati, today's Gochar transits, the Shodashvarga table — see below) and, when `year_wise_style` is given, the same cached year-wise forecast `GET /charts/{id}/year-wise` would return. Regenerated on every request (no PDF caching) since rendering is cheap pure-CPU HTML-to-PDF. As of #82, every Vedic-system section this engine computes is included, in this order: chart summary (planets/houses/ascendant/nakshatra), Avkahada Chakra, Ashtakvarga, the 16-varga Shodashvarga table (D2-D60; D1 is the chart summary above), Bhava Madhya/Chalit, Vimshottari Mahadasha/Antardasha, Yogini Dasha, Jaimini (Atmakaraka/Karakamsa/Swamsa/Char Dasha), KP sub-lords and cuspal sub-lords, Shadbala & Bhavabala, Lal Kitab chart, Planetary Friendship Table, Western + cuspal planetary aspects, detected yogas, Manglik & Kaal Sarp dosha, Sade Sati (lifetime timeline + Panoti), today's Transit (Gochar), predictions (chart-at-a-glance overview, ascendant narrative, Nakshatra Phal, the current Mahadasha/Antardasha reading with the next four sub-periods, key highlights for marriage/career/education/foreign settlement, the twelve-house Detailed Life Reading, per-Mahadasha-lord narrative — the overview, life reading and current-period reading are recomputed from the stored chart at download time, so charts saved before they existed still get them, and the current-period reading is always as of the download date), remedies, then the optional year-wise forecast. A Western-system chart only gets chart summary, aspects, yogas (none detected without houses from a sidereal chart — in practice empty), predictions/remedies are `null` (same Vedic-only restriction as the rest of this engine), and every other section above is simply omitted (its `result` key is `null`/absent). Known cosmetic limitation: dompdf's `page-break-inside: avoid` doesn't always prevent a long table's last couple of rows from visually crowding the fixed page footer when a section lands right at a page boundary — content is still fully present and correct, just tightly spaced in that specific case.

### Advanced free features
Competitor platforms charge (often subscription-tier) for these; this deployment offers them free, at the same self-hosted-engine precision as the rest of the Kundali Intelligence Suite (see "Open items" — sign/house-level accuracy, not arc-second). All are public, stateless (nothing persisted), and Vedic-only, same restriction as `nakshatra`/`dasha`/`yogas` above.

- `POST /doshas` → body: `{ name, dob, time, place }`. Returns `{ manglik: { is_manglik, from_ascendant: { afflicted, house }, from_moon: {...}, from_venus: {...}, cancelled, cancellation_reason, description }, kaal_sarp: { present, type, rahu_house, description } }`. Mangal/Kuja Dosha checks Mars from Ascendant, Moon, and (reported separately) Venus, with 2 documented cancellation conditions (own-sign/exalted Mars, Jupiter aspect). Kaal Sarp checks whether all 7 classical planets are hemmed between Rahu-Ketu, typed by Rahu's house (12 named types).
- `POST /sade-sati` → body: `{ name, dob, time, place, reference_date?: date }` (defaults to today). Returns `{ moon_sign, phase: "rising"|"peak"|"setting"|"none", is_active, cycle_start, peak_phase_start, setting_phase_start, cycle_end, reference_date, lifetime: { sade_sati: [{ phase, sign, start, end }], panoti: [{ type: "fourth_from_moon"|"eighth_from_moon", sign, start, end }] } }` — `phase`/`is_active`/`cycle_start`/`peak_phase_start`/`setting_phase_start`/`cycle_end` summarize the cycle relevant to `reference_date` (unchanged response fields from the original endpoint); `lifetime` is new and always covers the full ~100-year span from birth regardless of `reference_date`, computed once by a single deterministic forward sweep of Saturn's sign (fixing #66: `cycle_start` previously depended on which `reference_date` was queried for the very same real transit, since the old algorithm searched backward from that date and could land on either side of a Saturn retrograde station). A brief retrograde dip back across a sign boundary produces its own separate interval under the same phase label rather than being merged into the interval before/after it — matching how at least one major competitor platform presents the same real chart's Sade Sati table, not treated as a defect. `panoti` covers the two additional minor-difficulty transits (Saturn through the 4th/8th from natal Moon).
- `POST /kundali-matching` → body: `{ bride: { name, dob, time, place }, groom: { name, dob, time, place } }`. Returns Ashtakoot Guna Milan: `{ total_points, max_points: 36, minimum_recommended: 18, is_recommended, has_nadi_dosha, has_bhakoot_dosha, kootas: [{ name, points, max_points, description }] (8 entries: Varna, Vashya, Tara, Yoni, Graha Maitri, Gana, Bhakoot, Nadi), bride: { nakshatra, rashi }, groom: { nakshatra, rashi } }`. Scored purely from each partner's Moon nakshatra/sign, matching classical Ashtakoot practice. Vashya and Yoni use a documented simplified scoring table rather than the full classical gradient — see `app/Services/Astrology/Matching/Kootas/*`'s docblocks.
- `POST /panchang` → body: `{ date?: date (defaults to today), place }`. Returns the day's 5 "limbs": `{ date, tithi: { number, name, paksha }, nakshatra: { index, name, lord, pada }, yoga: { index, name }, karana: string, vaar: { name, lord }, sunrise, sunset, location_matched }`. `karana` is a plain name string, not an `{ index, name }` object like `yoga`/`nakshatra` — the classical scheme only names the karana, it has no independently useful numeric index (see `Panchang\Karana`'s docblock).
- `POST /numerology` → body: `{ name, dob }`. Returns `{ life_path: { number, meaning }, destiny: { number, meaning }, soul_urge: { number, meaning }, personality: { number, meaning } }` — Pythagorean numerology (Life Path from `dob`, Destiny/Soul Urge/Personality from `name`'s letters), Master Numbers 11/22/33 never reduced.
- `POST /dasha/pratyantardasha` → body: `{ lord, start: date, end: date }` — `lord`/`start`/`end` come from a specific entry in a prior `/chart` response's `dasha.mahadasha[].antardashas[]` or `dasha.yogini[].antardashas[]`. Returns `{ pratyantardashas: [{ lord, start, end }] }` (9 entries for Vimshottari lords; this endpoint is Vimshottari-only — Yogini's own 3rd-level subdivision isn't exposed). Deliberately a separate on-demand endpoint rather than part of `/chart`'s own response: eagerly returning all 729 leaf periods (9 Mahadashas × 9 Antardashas × 9 Pratyantardashas) for every chart request would bloat an already large payload for data almost no caller needs all at once.
- `POST /transits` → body: `{ name, dob, time, place, reference_date?: date }` (defaults to today). Returns `{ reference_date, natal_moon_sign, transits: { [planet: Sun..Ketu]: { sign, house_from_moon, text } } }` (#87; Gochar — each graha's sidereal sign at `reference_date`, counted into a house-from-the-natal-Moon per standard Gochar practice, with a templated narrative per planet — same "9 planets, house interpolated" scope choice as `dasha_narrative`, see `Predictions\TransitTemplates`'s doc comment). Date-dependent, not part of `/chart`'s own response, same reasoning as `/sade-sati` — also appears as a "Transit Today" section in the PDF report (`GET /charts/{id}/report`), computed fresh at download time there too.
- `POST /varga` → body: `{ name, dob, time, place, varga: "D1"|"D2"|"D3"|"D4"|"D7"|"D9"|"D10"|"D12"|"D16"|"D20"|"D24"|"D27"|"D30"|"D40"|"D45"|"D60" }`. Returns a single Shodashvarga divisional chart: `{ varga, ascendant: string, houses: [{ number, sign, planets: string[] }] (always 12, whole-sign), location_matched }`. Each of the 16 classical vargas is computed by its own fixed classical rule from the already-computed natal longitude (see `app/Services/Astrology/Varga/VargaCalculator.php` for the per-varga starting-sign rules, each cited to the classical trikona/kendra/element/modality pattern it follows) — pure arithmetic, no new astronomical calculation, so this inherits `/chart`'s existing sign-level precision. Separate endpoint rather than folded into `/chart`'s response since a caller only ever wants one varga at a time and `/chart`'s response is already large.

## Open items (flag if these need to change)

- **Placidus (`bhava_madhya`) precision decision (#80):** this engine implements REAL Placidus cusps (genuine semi-arc-trisection fixed-point iteration), not a simplified stand-in — the explicit choice the issue flagged as needing to be made ("pick one explicitly rather than silently presenting approximate Placidus cusps as precise"), consistent with the user's earlier choice to build "everything, including Placidus cusps" for this Phase 4 batch. That means `bhava_madhya` degrees carry this engine's existing Meeus/Standish-approximate longitude series PLUS the cusp geometry's own compounded approximation — not arc-second accuracy, same honesty standard as the rest of this engine. A specific textbook worked numerical example was sought for verification (common practice for this codebase's classical-algorithm citations) but the only one found was unreachable in this environment, and a secondhand web-search summary of its cited values didn't survive independent cross-checking (one number was off by double digits of degrees) — so verification instead relies on the cusp's own defining equation (checked against the output directly) and a fully self-derivable identity (cusps reduce to a direct RA-to-longitude conversion at the equator), both exact, rather than an unverifiable secondhand citation. See `Houses\PlacidusCusps`'s class docblock for the full reasoning. Known to perform irregularly above ±66° latitude (the classical Placidus "polar zone"), same scope limit as this engine's existing sunrise/sunset polar handling.
- **Lal Kitab's scope is deliberately narrower than the issue (#78) that requested it.** Only the fixed Aries-based chart construction and Pucca Ghar (own/strong house) for the 7 classical planets are implemented — both low-ambiguity and consistently described across every source this session could find. Rinn (karmic debt) detection, prediction text, and the Lal Kitab remedy library are NOT implemented: this session attempted web research for a specific, citable published edition (Wikipedia, archive.org's scanned Lal Kitab editions, astrosage.com, paramarsh.app, and a Scribd transcription were all tried), but every one of those domains was blocked by this environment's network egress policy, and the five original Lal Kitab editions are themselves in Urdu — not independently verifiable even if fetched. Falling back to this model's own general knowledge of the Rinn house-trigger table produced inconsistent recollections across cross-checks, so nothing from that was implemented either, rather than presenting an unverified guess as settled fact. Rahu/Ketu are also excluded from `pucca_ghar` for the same reason (sources disagree on which house each is conventionally given in Lal Kitab, commonly cited as either 6 or 12). Add Rinn/predictions/remedies once a specific, named, verifiable edition is chosen — see `LalKitab\LalKitabChart`'s class docblock for the full reasoning.
- **Avkahada Chakra's scope is deliberately narrower than competitor panels.** Varna/Yoni/Gana/Vashya/Nadi, "good planets"/"friendly signs" (derived from `PlanetaryFriendship`'s natural-friendship table), and "lucky stone"/"lucky day" (reusing `PlanetRemedies`' existing gemstone/fasting-day table) are included because each is backed by data this codebase already verified elsewhere. Paya and the "Favourable Points"/"Ghatak" (malefic) entries competitor reports also show — lucky numbers, good years, lucky metal, bad day/karan/lagna/month/nakshatra/tithi/yoga/planet — are not: without network access to cross-check a specific published classical source, and with no existing verified data in this codebase to derive them from, implementing them would mean presenting invented-sounding values with unwarranted confidence. Add them if/when a specific, citable source is identified.
- **Avastha's scope is deliberately 2 of 3 classical systems (#83).** Baladi (degree-in-sign age states) and Jagrat/Swapna/Sushupta (sign-dignity consciousness states) are both unambiguous, cross-verified across independent sources, and implemented in full. Deeptadi Avastha (a 9-state system) is NOT implemented: sources agree on the 9 states' names and their individual triggering conditions (exaltation, own sign, great-friend's sign, friend's sign, neutral sign, enemy's sign, debilitation, conjunction with a malefic, combustion), but not on how to resolve a planet matching more than one condition at once (e.g. own sign AND combust) — inventing a precedence rule without a verifiable source would mean presenting a guess as settled classical doctrine. Add it once a specific, citable source resolves the precedence question — see `Avastha`'s class docblock.
- Chart JSON shape is finalized above (#16). The calculation engine itself is a self-hosted, dependency-free implementation (Meeus low-precision Sun/Moon series, Standish's Keplerian planetary elements, whole-sign houses) rather than a Swiss Ephemeris binding — this build environment had no route to install/download one (no C compiler, no network access to Swiss Ephemeris's data files). Accuracy is good for correct sign/house placement, not arc-second precision. Geocoding is a small bundled gazetteer (PRD §8's named states/cities plus other major Indian/international cities) rather than a live geocoding API, for the same reason — unrecognized places fall back to Delhi/`Asia/Kolkata` (`location_matched: false`). Swapping either for the real thing later is contained to `app/Services/Astrology/`.
- **Kundali Intelligence Suite** (nakshatra/Vimshottari dasha, yoga detection, life-area predictions, remedies) extends the chart response above, all Vedic-only and computed on the same self-hosted engine — no external astrology package was added (evaluated and rejected `kunjara/jyotish`: GPL-2.0 license risk plus a compiled `swetest` binary dependency incompatible with this deployment target). Dasha transition dates use a 365.25-day/year approximation, so expect drift on the order of a day per decade against a table computed from the true sidereal year — consistent with this engine's existing sign/house-level precision, not arc-second accuracy. Yoga detection (`app/Services/Astrology/Yogas/`) and predictions (`app/Services/Astrology/Predictions/`) use simplified, documented classical rules rather than exhaustive classical-text coverage — see those namespaces' class docblocks for the specific simplifications (e.g. Neecha Bhanga checks 2 of several classical cancellation conditions). Predictions and remedies are gated by the new `Setting::astrology_predictions_enabled` flag (default on). Prediction/remedy text is currently English-only even though the template arrays are shaped for `en`/`hi`/`gu` — translating the generated prose (not just UI chrome) is unscheduled follow-up work.
- **Year-wise forecasts** (`POST /year-wise`, `GET /charts/{id}/year-wise`) live outside `birth_charts.result` in their own `year_wise_forecasts` table since, unlike the rest of the Kundali Intelligence Suite, they're date-dependent rather than immutable-at-birth. `style: "simplified"` samples transiting Jupiter/Saturn at a single fixed snapshot (July 1, noon UTC of the target year) rather than tracking exact sign-ingress dates within the year — a deliberate scope simplification. `style: "varshphal"` is a genuine second calculation engine (`app/Services/Astrology/YearlyForecast/`): it Newton-iterates a solar-return moment, casts a full return chart via the shared `ChartAssembler` (also used by the natal `BirthChartCalculator`), and derives Muntha/Varshesh/Saham from it. Varshesh uses a simplified 3-candidate dignity contest rather than full classical Panchadhikari, and only 8 of the ~16-32 classically-attested Sahams are implemented — both documented simplifications in `VarshphalCalculator`'s and `Saham`'s class docblocks.
- **PDF report** (`GET /charts/{id}/report`) uses `barryvdh/laravel-dompdf` (MIT-licensed, pure PHP, no system binaries — deploys cleanly on Laravel Cloud unlike a headless-Chrome approach) — the one new composer dependency added for this feature set.
